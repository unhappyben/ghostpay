The privacy model

Honest version: what each party learns, and what is cryptographically out of its reach.

The stealth math

ERC-5564 scheme 1, secp256k1 with view tags, keccak256 shared secret (sha256 for announcements made before 2026-09-08).

  • GenerateOne wallet signature derives spendPriv and viewPriv; the meta-address is spendPub ‖ viewPub. Same signature regenerates the same keys on any device.
  • DeriveThe sender picks ephemeral r, computes shared secret sh = keccak256(ECDH(r, viewPub)), and pays stealth = address(spendPub + sh·G).
  • AnnounceThe network sees (stealth, ephPub = r·G, viewTag = sh[0]). Nobody can link stealth to the meta-address without viewPriv.
  • ScanThe recipient recomputes sh = keccak256(ECDH(viewPriv, ephPub)) per announcement; the view tag filters 255/256 of them cheaply. Watching needs only the viewing key.
  • SpendThe stealth private key is spendPriv + sh. It exists only in the session that re-derives it, signs the sweep, and is never stored.

What the relayer cannot do

The sweep artifact is two signatures. The EIP-712 SweepIntent, signed by the stealth key, binds the action, token, destination, Privacy Pools precommitment, fee, and deadline. The EIP-7702 authorization binds the delegation target and the nonce. Change any byte and a signature stops verifying: the relayer's only options are to deliver the payload as signed or to censor it. It cannot redirect funds, raise the fee, or reuse the artifact. The withdrawal relay is bound the same way by the circuit: the context signal commits the proof to the exact recipient, fee recipient, and fee rate.

Censorship is still possible. The mitigation is that any 7702-capable broadcaster can carry the same signed artifact: relay.mjs broadcasts a saved artifact from any funded key, and nothing about the artifact is tied to this relayer.

The USDC pool path

USDC can also move gaslessly without the pool: an EIP-3009 transferWithAuthorization signed by the stealth key sends the balance straight to a destination. Gasless, but public: the one-time address and the destination are linked onchain for anyone reading the transfer. Sweeping into the mainnet USDC Privacy Pool instead (intent action 2) breaks that link: the deposit is public, the later withdrawal lands at an address with no onchain connection to the one-time address that was paid.

  • Minimum. The pool refuses deposits below 25 USDC. The app enforces the minimum on the post-fee amount (balance minus the relayer fee), so a balance that would land under 25 USDC never arms a pool sweep.
  • Vetting fee. The pool takes a 50 bps vetting fee on the deposited amount, deducted onchain before escrow; the app reads the net amount from the deposit event.
  • ASP screening. The deposit must be approved by the association-set provider before it can be withdrawn. Usually hours. The funds are safe while they wait; the withdrawal is the same gasless ZK withdrawal as the ETH pool.
  • Same secret discipline. The pp-secret file downloads at arm time and the backup gate blocks the broadcast until the file is confirmed, exactly as for ETH pool sweeps.

Shrinking the footprint

Fund the runner from Privacy Pools

A runner funded from an operator wallet links every relayed transaction to the operator onchain. Funded from a Privacy Pools withdrawal instead, the runner has no funding link to anyone. Rotate runners by withdrawing again to a fresh address. Procedure: Relayer.

Jitter

Every broadcast waits a random delay (announce 2-15s, sweeps and withdrawals 5-45s) so the browser request and the onchain transaction are not trivially time-correlated. This weakens timing analysis; it does not defeat a patient observer.

Flashbots Protect

Broadcasts default to Protect's private mempool: pending transactions are invisible to explorers and public mempool watchers until mined. There is no public pending transaction to correlate with your request.

Tor + RPC rotation

Relayer-side, every JSON-RPC call goes to a random endpoint from RPC_URLS, and TOR_PROXY routes all of it over Tor: no single RPC provider sees both the relayer's IP and its broadcasts.

Onion service

The strongest option: serve the app itself as a Tor onion service, so the browser-to-relayer hop is Tor too and the relayer never sees your IP at all.

# torrc
HiddenServiceDir /var/lib/tor/ghostpay/
HiddenServicePort 80 127.0.0.1:8791

Restart tor, read the hostname from /var/lib/tor/ghostpay/hostname, open that .onion address in Tor Browser.

Metadata and memos

The announcement metadata is public calldata, forever. The default is one byte: the view tag. The invoice suite's encrypted memo format ([viewTag(1)][R(33)][nonce(12)][AES-GCM ciphertext]) decrypts only with the recipient's viewing key; the AES key is keccak256(ECDH(r, viewPub) ‖ "memo"). The relayer and the chain see ciphertext and its length. The length is the leak: a long metadata betrays that a memo exists. Never put plaintext identifying information in metadata.

ZK proves, it does not hide from the prover

A zero-knowledge proof hides the witness from the verifier, not from the machine that computed the proof. The withdrawal proof is built in the browser for exactly this reason: server-side proving would hand the server the nullifier and secret. The same argument kills server-side stealth-address generation: the server would hold the keys. The correct construction is the one this repo has: client-side generation and proving, payer-side announce, anonymous transport (Tor) on the remaining relayer hops, and blind-signature metering if request counts ever need hiding from the relayer. For private scanning and metering respectively, see ePrint 2021/1256 (Oblivious Message Retrieval) and RFC 9576 (Privacy Pass, Anonymous Rate-Limited Credentials).

Residual leaks, plainly

  • The relayer sees IP + timing unless you reach it over Tor. That is one party, and it is the party you chose to run or use.
  • Batch sweeps share one transaction: the swept stealth addresses are linked onchain. Sweep individually when linkage matters.
  • The payer's payment to the stealth address is a normal public transfer. Stealth addresses hide the recipient's identity, not the existence of the payment; the companion essay (How Much Stealth Does a Stealth Address Get You?) covers what leaks at spend time, which is what the Privacy Pools sweep fixes.
  • Withdrawals wait on ASP approval. The ASP is a compliance gate operated by the Privacy Pools deployment, not by ghostpay.
  • The stealth crypto follows the ERC-5564 reference but is hand-rolled, and the sweeper contracts are unaudited. Prototype software.
